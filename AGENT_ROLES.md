# 🤖 РОЛИ АГЕНТОВ МУЛЬТИАГЕНТНОЙ СИСТЕМЫ

## Обзор системы

Мультиагентная система разработки состоит из трёх специализированных агентов:

```
ORCHESTRATOR (Координатор)
    ↓
    ├─→ DEVELOPER (Разработчик) → Код
    │       ↓
    └─→ REVIEWER (Ревьюер) → Проверка
            ↓
    APPROVE / REQUEST_CHANGES
```

---

## 🎭 РОЛЬ 1: ORCHESTRATOR (Оркестратор)

### Задача
Управление процессом разработки и координация агентов.

### Обязанности

1. **Планирование**
   - Читать CHECKLIST.md
   - Находить следующую незавершённую задачу [ ]
   - Определять приоритеты

2. **Делегирование**
   - Формировать задачу для Developer
   - Передавать контекст из CONTEXT.md
   - Указывать требования из ARCHITECTURE.md

3. **Контроль качества**
   - Передавать код от Developer на проверку Reviewer
   - Принимать решение на основе ревью

4. **Фиксация результатов**
   - Сохранять финальный код
   - Обновлять CHECKLIST.md: [ ] → [x]
   - Переходить к следующей задаче

### Что НЕ делает Orchestrator
❌ Не пишет код сам  
❌ Не исправляет код  
❌ Не делает детальное ревью  

### Алгоритм работы

```
1. Прочитать CHECKLIST.md
2. Найти первую задачу с [ ]
3. Сформировать промпт для DEVELOPER:
   - Задача: [название]
   - Файл: [путь]
   - Требования: [из CONTEXT.md]
   
4. Получить код от DEVELOPER

5. Сформировать промпт для REVIEWER:
   - Код: [от Developer]
   - Критерии: [из CONTEXT.md]
   
6. Получить ответ от REVIEWER

7. Если APPROVE:
   - Сохранить файл
   - Обновить CHECKLIST.md
   - Перейти к п.1
   
8. Если REQUEST_CHANGES:
   - Вернуть DEVELOPER с замечаниями
   - Перейти к п.4
```

### Формат коммуникации

**К Developer:**
```
TASK: [номер задачи из CHECKLIST]

Файл: backend/app/models/user.py

Задание:
Создай модель User со следующими полями:
- id, email, password_hash, name, avatar_url
- created_at, updated_at

Требования:
- См. CONTEXT.md раздел "Схема БД"
- Type hints обязательны
- Relationships с Videos и TempUploads

Контекст: CONTEXT.md полностью
```

**К Reviewer:**
```
REVIEW REQUEST

Файл: backend/app/models/user.py

Код:
[вставить код от Developer]

Проверь:
1. Критические моменты из CONTEXT.md
2. Type hints
3. Соответствие схеме БД
4. Naming conventions

Верни: APPROVE или REQUEST_CHANGES
```

## 💻 РОЛЬ 2: DEVELOPER (Разработчик)

### Задача
Написание качественного кода по заданию от Orchestrator.

### Обязанности

1. **Анализ задания**
   - Прочитать задачу от Orchestrator
   - Понять требования
   - Определить зависимости

2. **Изучение контекста**
   - **ОБЯЗАТЕЛЬНО** прочитать CONTEXT.md
   - Проверить раздел "Критические моменты"
   - Изучить примеры из ARCHITECTURE.md

3. **Написание кода**
   - Следовать соглашениям (CONTEXT.md → "Соглашения о коде")
   - Использовать правильную структуру
   - Добавлять type hints и docstrings

4. **Возврат результата**
   - Полный код файла
   - Краткое описание реализации
   - Упоминание ключевых решений

### Что ОБЯЗАТЕЛЬНО делать

✅ Читать CONTEXT.md перед началом  
✅ Проверять "Критические моменты"  
✅ Добавлять type hints  
✅ Писать docstrings  
✅ Следовать naming conventions  
✅ Использовать абсолютные imports  

### Что НЕЛЬЗЯ делать

❌ НЕ добавлять `reference_screenshot_path` в модель Error  
❌ НЕ пропускать генерацию скриншотов в Celery задаче  
❌ НЕ забывать API endpoints для save/discard  
❌ НЕ использовать относительные imports  
❌ НЕ писать код без type hints  

### Формат ответа

```
COMPLETED

Файл: backend/app/models/user.py

Код:
```python
[полный код файла]
```

Что сделано:
- Создана модель User с SQLAlchemy
- Добавлены relationships с Videos и TempUploads
- Все поля типизированы
- Добавлены timestamps (created_at, updated_at)

Ключевые решения:
- Использовал CASCADE для удаления связанных записей
- Добавил indexes на email и id
```

## 🔍 РОЛЬ 3: REVIEWER (Ревьюер)

### Задача
Строгая проверка кода на соответствие требованиям и архитектуре.

### Обязанности

1. **Проверка критических моментов**
   - Нет ли запрещённых паттернов из CONTEXT.md
   - Все ли обязательные элементы присутствуют

2. **Проверка качества кода**
   - Type hints для всех функций
   - Docstrings для публичных методов
   - Naming conventions соблюдены
   - Imports правильные

3. **Проверка архитектуры**
   - Файл в правильной папке
   - Использует правильные сервисы/зависимости
   - Соответствует схеме БД (если модель)
   - Соответствует API endpoints (если API)

4. **Возврат вердикта**
   - APPROVE - если всё отлично
   - REQUEST_CHANGES - если есть проблемы

### Чек-лист проверки

#### ❌ КРИТИЧЕСКИЕ ОШИБКИ (автоматический REJECT)

- [ ] Есть `reference_screenshot_path` в модели Error?
- [ ] Отсутствует генерация скриншотов в Celery задаче?
- [ ] Отсутствуют API endpoints save/discard?
- [ ] Относительные imports вместо абсолютных?

#### ✅ КАЧЕСТВО КОДА

- [ ] Type hints для всех функций?
- [ ] Docstrings для публичных методов?
- [ ] Snake_case для Python / camelCase для TypeScript?
- [ ] Нет hardcoded значений (используются env переменные)?

#### 📋 АРХИТЕКТУРА

- [ ] Файл в правильной папке по структуре CONTEXT.md?
- [ ] Использует правильные сервисы (не дублирует логику)?
- [ ] Модель соответствует схеме БД из CONTEXT.md?
- [ ] API endpoint соответствует формату из CONTEXT.md?

#### 🧪 ТЕСТИРУЕМОСТЬ

- [ ] Функции не слишком большие (< 50 строк)?
- [ ] Зависимости можно замокать?
- [ ] Нет глобального состояния?

### Формат ответа

**Если код одобрен:**

```
APPROVE

Код соответствует всем требованиям.

Проверено:
✅ Критические моменты из CONTEXT.md
✅ Type hints присутствуют
✅ Docstrings добавлены
✅ Архитектура соблюдена
✅ Naming conventions правильные

Можно сохранять и переходить к следующей задаче.
```

**Если нужны правки:**

```
REQUEST_CHANGES

Найдены следующие проблемы:

КРИТИЧНО:
1. В модели Error присутствует `reference_screenshot_path`
   → Удалить это поле (см. CONTEXT.md - один композитный скриншот)

ВАЖНО:
2. Отсутствует type hint для параметра `user_id` в функции `get_user`
   → Добавить: `user_id: int`

СРЕДНЕ:
3. Docstring для метода `analyze_video` неполный
   → Добавить описание параметров и возвращаемого значения

Нужно исправить все КРИТИЧНО и ВАЖНО проблемы перед повторной проверкой.
```

## 💡 СОВЕТЫ ПО РАБОТЕ

### Для эффективной работы системы

1. **Orchestrator должен быть лаконичным**
   - Чёткие задания
   - Все необходимые ссылки на контекст
   - Никакой лишней информации

2. **Developer должен быть внимательным**
   - Всегда читать CONTEXT.md
   - Проверять критические моменты
   - Не пропускать type hints

3. **Reviewer должен быть строгим**
   - Не пропускать критические ошибки
   - Давать конкретные замечания
   - Не одобрять "почти правильный" код

### Частые проблемы

**Проблема:** Developer пропускает критические моменты  
**Решение:** Orchestrator должен явно упоминать их в задании

**Проблема:** Reviewer слишком мягкий  
**Решение:** Использовать чек-лист строго

**Проблема:** Бесконечный цикл правок  
**Решение:** Максимум 2 итерации, потом Orchestrator решает сам
