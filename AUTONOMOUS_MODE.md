**Система работает автономно по плану. Уточняйте у пользователя ТОЛЬКО спорные вопросы.**

---

## 🎯 ПРИНЦИП АВТОНОМНОСТИ

### ✅ Агенты решают САМИ:

- Техническая реализация (как писать код)
- Выбор структур данных
- Названия переменных/функций
- Порядок выполнения в рамках дня
- Мелкие архитектурные детали

### ⚠️ Агенты спрашивают ПОЛЬЗОВАТЕЛЯ:

- Неоднозначности в требованиях
- Противоречия в документации
- Критические архитектурные решения (не описанные в CONTEXT.md)
- Если не хватает данных (API ключи, пути к файлам)
- Если есть несколько равнозначных вариантов

## 🚀 РЕЖИМ РАБОТЫ: AUTONOMOUS

### Orchestrator в автономном режиме

**Алгоритм:**

```
1. Прочитать FULL_MVP_PLAN.md
2. Найти текущий день/задачу (по CHECKLIST.md)
3. Выполнить ВСЕ задачи этого дня:
   
   ДЛЯ КАЖДОЙ задачи:
   a) Делегировать Developer
   b) Получить код
   c) Делегировать Reviewer
   d) Если APPROVE → сохранить и следующая
   e) Если CHANGES → вернуть Developer (макс 2 итерации)
   f) Обновить документацию
   
4. После завершения дня:
   - Обновить PROGRESS.md
   - Сделать git commit
   - Вывести отчёт пользователю
   - Спросить: продолжить следующий день?

5. Если встретил СПОРНЫЙ ВОПРОС:
   🛑 ОСТАНОВИТЬСЯ
   📝 Сформулировать вопрос для пользователя
   ⏸️ Ждать ответа
```

## 🧠 КАК ОПРЕДЕЛИТЬ "СПОРНЫЙ ВОПРОС"

### ✅ НЕ спорные (решаем сами):

**Пример 1: Названия переменных**
```
❌ НЕ спрашивать: "Назвать переменную user_data или userData?"
✅ Решить: использовать snake_case (user_data) согласно CONTEXT.md
```

**Пример 2: Порядок полей**
```
❌ НЕ спрашивать: "В каком порядке указать поля в модели?"
✅ Решить: id, foreign keys, обычные поля, timestamps
```

**Пример 3: Детали реализации**
```
❌ НЕ спрашивать: "Использовать list comprehension или цикл for?"
✅ Решить: использовать что проще и читабельнее
```

**Пример 4: Мелкие улучшения**
```
❌ НЕ спрашивать: "Добавить дополнительную валидацию email?"
✅ Решить: следовать MVP плану, не добавлять лишнего
```

### ⚠️ СПОРНЫЕ (спрашиваем):

**Пример 1: Противоречие в документах**
```
✅ Спросить:
"В CONTEXT.md сказано X, но в ARCHITECTURE.md сказано Y.
Что использовать?"
```

**Пример 2: Неоднозначное требование**
```
✅ Спросить:
"План говорит 'валидация файла', но не указано какая именно.
Проверять только формат или ещё что-то?"
```

**Пример 3: Критическое архитектурное решение**
```
✅ Спросить:
"В плане не описано как хранить временные файлы.
Вариант A: в оперативной памяти
Вариант B: на диске
Что выбрать?"
```

**Пример 4: Отсутствие данных**
```
✅ Спросить:
"Не найден ANTHROPIC_API_KEY в .env
Предоставьте ключ для продолжения"
```

**Пример 5: Несколько равноценных путей**
```
✅ Спросить:
"Для реализации X есть 2 подхода:
A) [описание + плюсы/минусы]
B) [описание + плюсы/минусы]
Оба подходят. Какой предпочесть?"
```

## 📋 ПРАВИЛА АВТОНОМНОЙ РАБОТЫ

### 1. Следовать плану строго
- Выполнять задачи в порядке из FULL_MVP_PLAN.md
- Не пропускать задачи
- Не добавлять задачи (только если не критично)

### 2. Решать технические вопросы самостоятельно
- Как писать код → решает Developer
- Качество кода → решает Reviewer
- Координация → решает Orchestrator

### 3. Спрашивать только важное
- Спорные архитектурные решения
- Противоречия в документации
- Отсутствие критических данных

### 4. Документировать всё
- Каждый файл → в DEVELOPMENT_LOG.md
- Каждое ревью → в REVIEW_LOG.md
- Каждое решение → в DECISIONS.md
- Прогресс → в PROGRESS.md

### 5. Делать коммиты регулярно
- После каждого завершённого дня
- Сообщение коммита:
  ```
  feat(week1-day2): completed 12 tasks
  
  - Created models: User, Video, Analysis, Error, TempUpload
  - Set up database session and config
  - Added initial migration
  
  Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>
  ```

### 6. Отчитываться пользователю
- В конце каждого дня
- При спорных вопросах (сразу)
- При критических ошибках (сразу)
